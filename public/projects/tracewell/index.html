The problem

Nothing crashes. Nothing alerts. The pipeline just quietly stops making progress.

These pipelines advance in strict sequence, only once each order reaches a terminal state. One stuck order backs up the whole queue — and error-rate monitors never see it, because nothing throws. Finding the culprit means tracing timestamps across days of logs by hand.

What it does · four steps

{{ stepHint }}
01

Scans continuously

every 30s

Four classes of anomaly: a record stuck in a non-terminal state, a backlog piling up behind it, a burst of sync failures, and a gap in new records arriving at all. Findings are deduped so they don't re-fire, and auto-resolve when the condition clears.
02

Investigates on its own

agent loop

A Claude agent with a fixed set of read-only database tools pulls the record's history, compares it against healthy neighbours, and follows whatever the evidence points to. No human writes the query that finds the answer.
03

Writes a structured report

strict schema

Root cause, confidence, affected records, a step-by-step evidence trail and recommended actions. Not a chat transcript — a schema-enforced result you can render, store, or pipe into a ticket.
04

Shows it on a dashboard

live

Pipeline health at a glance, the incident list with severity and status, each report in full, and the raw record table with every row expandable to its event history.

The test case

One order in the wrong currency, 50 orders stuck behind it, and nothing labelled as the cause.

The seed script builds a deterministic scenario: 300 healthy orders, order #301 priced in MXN that reaches AWAITING_SETTLEMENT and never confirms, and orders #302–#351 discovered normally but never synced. Nothing in the data points at the currency.

What the agent found, unprompted
01 Sampled the healthy orders: all USD, all settling within minutes.
02 Noticed #301 is the only MXN order — and the only order not in a terminal state.
03 Named the currency mismatch as the root cause, with high confidence.
04 Called the 50-order backlog a symptom of the pipeline's sequential design, not a second problem.

Why it's practical

It catches what alerting misses +
Error-rate monitors are blind to a pipeline that stops making progress without failing. This targets that gap specifically.
The expensive part is automated +
Anyone can write a query that says 51 orders are unsynced. Finding which one is the cause is the part that took days by hand.
Cheap to run +
The scanner is plain SQL on a timer. The paid agent call only happens when something is actually flagged.
Built to extend +
Point DATABASE_URL at a read replica and adjust the schema and detectors to your columns. A new failure class is one new file; more agent context is one new tool.

Deliberately out of scope · 5

+

Built to demonstrate the concept end to end, including a live, unscripted investigation. It does not run against production traffic, and the gaps are on purpose.

No auth — the API and dashboard never leave localhost.
No automated tests — verified against live scans and live agent runs. Production would need tests on detector thresholds and a recorded transcript for the tool loop.
No cost guardrails beyond a 12-call cap per investigation.
No multi-instance coordination — two replicas would each scan; a real deployment needs an advisory lock.
Polling, not push — fine at this scale, not at many concurrent viewers.

Run it locally in three commands.

export ANTHROPIC_API_KEY=sk-ant-…
docker compose up --build -d postgres server web
docker compose --profile seed run --rm --build seed

The backlog incident appears within a minute of seeding, with the agent's report following shortly after. Without an API key the scanner still detects and lists incidents — it just skips the investigation step.
