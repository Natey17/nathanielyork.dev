Searching for a real edge in market data.

A research engine that tests whether a trading idea actually holds up statistically — or correctly proves it doesn't.

Edgeine is a statistics and machine-learning pipeline that searches historical futures market data for a genuinely profitable, persistent trading edge. Finding one is the objective — if one is there to be found at all.

Most of the code is statistical gates and falsification tests, because in this domain almost everything that looks like an edge isn't one. A discovery is only worth acting on if it survives a system built to break it — so "no" has to be an answer the pipeline can reach, or a "yes" means nothing.

It is not a trading bot: no order execution, no live data, and no path to either. This is the research that would have to come first.

02 · Why it exists

Symmetric by design

The system must be equally capable of proving an apparent edge is overfit noise as confirming a real one. Every statistical gate exists to reject false positives, not to produce impressive-looking numbers.

Data decides the ceiling

A result is only as trustworthy as the tier it came from. A correlation found on free, two-year-lookback data is useful for generating hypotheses and is structurally never allowed to become a certified edge.

Every claim traceable

Nothing is a number in a printout with no record of how it was produced. Raw data is never mutated — corrections arrive as new, provenance-tracked ingestion runs, not silent overwrites.

03 · Architecture

raw_bars → clean_bars

Vendor ingestion, tagged with a data tier and a provenance record. Raw bars are immutable.

features

As-of joined, registry-declared features — computed only from information available at the setup's timestamp.

setups → setup_outcomes

Triple-barrier labelling. Every outcome is R-multiple normalized, so instruments and contract-quarters pool directly.

hypotheses

Pre-registered, then Stage 1 screened against the development sample only.

experiments

Backtest, walk-forward and statistical test, each persisted with its config snapshot.

robustness_results

Phase 4's four lenses, run on the development sample and AND-gated.

edges

Reachable only through one explicit, human-gated command that reads the sacred holdout.

One direction, no shortcuts

Each stage writes to the next and to the database, never back over its input. Because everything downstream of labelling is expressed as a multiple of the trade's own risk, results across different instruments, contract sizes and periods are directly comparable and poolable — without a spliced continuous-contract price series, which is deliberately left to a paid vendor rather than DIY'd.

Seven command-line entrypoints drive it; a read-only Streamlit dashboard reads what they wrote.

04 · Data tiers

Not a convention enforced by discipline. The certification script calls require_validation_tier() and hard-stops before it will even read the sacred holdout if any instrument behind a candidate isn't validation-tier. No amount of exploratory data, however much accumulates, can cross that gate.

05 · Where it stands

Proven end to end on planted signals

Every piece of the pipeline through certification has been proven correct against synthetic fixtures with known, planted signals — including a fixture designed specifically to clear every Stage 2 gate while still being regime-concentrated, which Phase 4 correctly catches and rejects.

No certified edges exist today, which is the expected state rather than a gap: no validation-tier data has been purchased yet, so certification correctly hard-stops on every real instrument.

Unit tests favour hand-verified arithmetic and named trap cases over smoke tests — for example, a test proving a block bootstrap's confidence interval is genuinely wider on autocorrelated data than on i.i.d. data, not merely that the code runs.

Four gates, then four attempts to break it.

Screening is cheap and lenient and makes no claim. Confirmation is where a claim is made. Robustness testing then exists only to try to destroy that claim, and certification touches the holdout once.

Stage 1 · Screening

A filter, not a claim

Every hypothesis in the pre-registered space is screened against the development sample only — the sacred holdout is carved out and excluded before this ever runs. One hypothesis per continuous feature, tested via point-biserial correlation; one per categorical feature value, tested as a 0/1 indicator.

Deliberately loose at alpha = 0.20. Its only job is to avoid running the expensive Stage 2 test on hypotheses that are obviously nowhere close.

Stage 2 · Confirmatory testing

Stage 1 survivors run through purged, embargoed walk-forward cross-validation. A hypothesis reaches candidate only if it clears all four gates below — documented everywhere in the codebase as a human review checkpoint, not a certified edge.

Gate 01

N ≥ 100 out-of-sample trades

Below this the hypothesis terminates at insufficient_data — a correct outcome, not a failure.

Gate 02

BH-FDR corrected p < 0.05

Benjamini-Hochberg correction across the whole Stage 2 family tested together in one run — not the full Stage 1 space, and not across separate runs.

Gate 03

Effect size ≥ 0.15R

Statistically significant but economically trivial effects don't qualify on significance alone.

Gate 04

Stability and deflated Sharpe

At least 65% of walk-forward folds agreeing in sign with the aggregate effect, plus a deflated Sharpe ratio ≥ 0.95 — Bailey and López de Prado, correcting for how many hypotheses were tried.

Phase 4 · Falsification

A candidate is not trusted yet. Phase 4's job is to aggressively try to break it, through four lenses that are all AND-gated: passing one never compensates for failing another.

Monte Carlo block bootstrap

The only p-value surface in this phase, eligible for batch BH-FDR correction across multiple candidates certified together. Circular block resampling rather than i.i.d., so path-dependent statistics like maximum drawdown reflect real trade-sequence autocorrelation.

Volatility-regime stability

Does the effect exist across at least two well-populated volatility regimes, or only in one narrow slice of history? Fails closed — not a silent skip — if there isn't enough regime diversity to even assess it.

Parameter sensitivity

Does the effect survive nearby label-rule variations, at 0.75× to 1.5× the candidate's own target, or is it an artifact of one exact parameter choice?

Cost sensitivity

Does the effect survive twice the assumed commission and slippage, or does it evaporate the moment trading gets slightly more expensive?

Regime and sensitivity checks are deliberately sign-agreement and magnitude checks against point estimates, never fresh significance tests — keeping exactly one p-value surface anywhere in this phase, so robustness testing can never become a second, uncorrected source of multiple testing.

Certification · The sacred holdout

Touched at most once

A slice of each dataset — 15% by default — is carved out before Stage 1 ever runs and is never touched by anything except one explicit, human-gated final step.

Two independent guards enforce that in code rather than convention: the function that reads the holdout requires the hypothesis to be at robustness_passed, and certification refuses to run a second time on a hypothesis that has already reached a terminal status.

Known limitations

Accepted and documented rather than quietly swept under the rug.

Cross-run multiple testing

BH-FDR is scoped to one script invocation's Stage 2 family, not the research program's entire history. Tracked for human-reviewer awareness.

Commission estimates

Most instruments' costs come from real broker rate schedules cross-referenced against two independent brokers — a reasonable estimate, not a verified quote.

Regime testing has limited teeth

Not for want of implementation: there isn't yet enough real history to populate multiple distinct volatility regimes.
